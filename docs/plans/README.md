# Планы реализации Paper Cat World PoC

Этот каталог превращает [дизайн-документ](../design-doc.md) в шесть последовательно исполнимых инженерных этапов. Каждый этап заканчивается работающим инкрементом, автоматическими тестами и коротким ручным демо. Следующий этап начинается только после выполнения checklist предыдущего.

## Порядок и зависимости

| Этап | План | Проверяемый результат |
| --- | --- | --- |
| 1 | [Геометрическое ядро](01-geometric-core.md) | Вложенная бумажная сцена работает без браузера и рендера |
| 2 | [Стол и манипуляция](02-table-interaction.md) | Тестовые бумажные объекты раскладываются и вкладываются на интерактивном столе |
| 3 | [Рисование и вырезание](03-drawing-and-cutting.md) | Нарисованный контур превращается в отдельную игровую деталь |
| 4 | [Коты и одежда](04-cats-and-clothing.md) | Одна и та же одежда стабильно надевается на разных котов |
| 5 | [Листы и тетради](05-sheets-and-notebooks.md) | Коты перевозятся во вложенных листах между комнатами |

Зависимость линейная: `1 → 2 → 3 → 4 → 5 → 6`. План может уточнять реализацию уже введённого интерфейса, но не ломать его без отдельного изменения дизайн-документа и всех зависимых планов.

## Общий технический контракт

- Язык — JavaScript с ES modules. Переход на TypeScript в PoC не планируется.
- Менеджер пакетов — npm; приложение собирается Vite, сцена отображается PixiJS.
- Vitest проверяет ядро и интеграции без браузера. Playwright проверяет desktop Chromium и профиль мобильного WebKit. Firefox проходит ручной smoke-тест на шестом этапе.
- `src/core/index.js` — единственная точка изменения мира для приложения. Ядро не импортирует PixiJS и не обращается к DOM, Canvas, файловым API, `Date.now`, `Math.random` или размерам экрана.
- Основной API последовательно формируется как `createWorld`, `applyCommand`, `validateWorld`, `serializeWorld` и `loadWorld`. До шестого этапа экспортируются первые три функции; сохранение добавляет последние две без изменения командного API.
- `applyCommand(world, command)` не изменяет аргументы. Успех имеет форму `{ ok: true, world, events }`, отказ — `{ ok: false, world, error: { code, message, details } }`. При отказе возвращается исходная ссылка `world`, а `events` отсутствует.
- Идентификаторы, отметки времени и другие недетерминированные значения создаёт приложение и передаёт в команде. Одинаковые `world` и `command` всегда дают одинаковый результат.
- Состояние нормализовано в словарях `entities`, `surfaces` и, начиная с этапа 3, `drawings`. Сущность расположена на поверхности через `surfaceId`; поверхность принадлежит сущности через `hostEntityId` либо является корневой.
- In-memory `world.rules` содержит нормализованные plain-data правила текущей сборки: геометрические допуски, диапазоны трансформаций и, с этапа 4, реестр шаблонов. Команды и `validateWorld` читают их из мира; сериализатор не сохраняет asset/template definitions, а загрузчик получает актуальный config приложения заново.
- Все координаты домена измеряются в логических единицах мира или локальной поверхности. CSS-пиксели и screen-space существуют только в приложении и рендерере.
- Любая команда сначала полностью проверяется, затем атомарно создаёт новое состояние. Частично применённых изменений не бывает.

## Соглашения о реализации

- Трансформация имеет форму `{ x, y, rotation, scale }`, где угол задан в радианах, а `scale` — положительное конечное число. Матрицы используются внутри геометрии, но сохраняемая модель остаётся читаемой.
- Точка привязки сущности — локальный `(0, 0)`. Именно она проверяется на попадание в допустимую область целевой поверхности.
- Для сравнения геометрии используется именованная константа допуска, а не точное равенство чисел с плавающей точкой.
- Временные состояния — выбор, активный инструмент, указатели, drag-preview, камера, анимации и графические кэши — не записываются в доменный мир.
- Визуальные анимации не меняют правила ядра: ядро сразу возвращает конечное состояние, а рендерер интерполирует между предыдущим и новым представлением.
- Параметры из раздела 15 дизайн-документа задаются через `createWorld(config)` и нормализуются в `world.rules` либо находятся в данных шаблонов. Они не превращаются в разбросанные по коду константы.

## Общие команды проекта

К завершению соответствующих этапов должны существовать следующие npm scripts:

```text
npm run dev                         локальный Vite-сервер, с этапа 2
npm run build                       production-сборка, с этапа 2
npm test                            однократный запуск Vitest, с этапа 1
npm run test:watch                  Vitest в watch-режиме, с этапа 1
npm run demo:core                   headless-демо ядра, с этапа 1
npm run test:e2e                    Playwright, с этапа 2
```

Playwright содержит проекты `chromium` с viewport 1440×900 и `mobile-webkit` на основе device profile `iPhone 13`; второй использует WebKit, touch и мобильный viewport. Конфигурация сама запускает Vite preview/dev server, поэтому тесты не требуют вручную поднятого сервера.

## Определение готовности этапа

Этап завершён, только если одновременно выполнено следующее:

- реализованы все его изменения модели и публичных интерфейсов;
- новые ошибки имеют стабильные коды и проверены негативными тестами;
- `npm test` проходит, а с этапа 2 проходят оба обязательных Playwright-проекта;
- `npm run build` завершается без ошибок, если браузерное приложение уже существует;
- ручное демо из плана воспроизводится с нуля без изменения состояния через DevTools;
- не нарушены инварианты раздела 10 и границы PoC раздела 11 дизайн-документа;
- README или комментарии документируют только неочевидные публичные договорённости, но не дублируют дизайн-документ.

Календарные оценки в планы намеренно не входят. Если критерий готовности не проходит, следующий этап не используется для маскировки долга предыдущего.
