## Резюме

Ядро сделано аккуратно и честно соответствует своему контракту: оно детерминировано, не знает про браузер, возвращает `{ ok, world, events }` и атомарно откатывается при отказе. Инварианты из §10 дизайн-документа реально проверяются в `validateWorldState`, а не только описаны. Есть регрессионные тесты на **точное** равенство трансформаций после дропа — ровно то, чего требует `AGENTS.md`, и это заметно лучше, чем обычная проверка «дроп прошёл».

Проблемы сосредоточены в трёх местах:

1. **Ветка ломает e2e-сценарий вложенности листов** — регрессия, введённая коммитом `09b6fea`. Корневая причина найдена и воспроизведена вне браузера.
2. **Стоимость команды растёт квадратично от числа вырезанных деталей.** 5 вырезок с реалистичным контуром → 20 мс на одну команду, ~41 мс на один дроп. Это бьёт ровно по главному циклу PoC («нарисовал → вырезал → положил»).
3. **Заявленная в дизайн-документе защита от этой проблемы не реализована**: `DrawingTextureCache` не кэширует текстуры, а редактор перерисовывает все штрихи на каждый `pointermove`.

## Блокеры

### B1. Регрессия: лист больше не вкладывается в другой лист

**Файл:** [src/app/interaction-controller.js:11](src/app/interaction-controller.js:11)
**Тест:** `tests/e2e/table.spec.js:61` «nests one sheet in another and moves the hidden tree»
**Ожидается** `data-created-sheet-surface="sheet-created-1-inside"`, **получено** `"table"`.

Bisect по пяти коммитам ветки (в изолированном worktree, прогон одного теста на каждом коммите):

```
13a5e66 -> passed
6aeaa0a -> passed
09b6fea -> FAILED   <- регрессия здесь
dc51d15 -> FAILED
c48d4c6 -> FAILED (HEAD)
```

`09b6fea` ввёл `surfaceCandidatesForDrop`, которая переупорядочивает кандидатов, опираясь на `hits[0]`. Проблема в том, что **`hits[0]` — это сам перетаскиваемый объект**: hit-тест работает по модельным координатам, а модель во время жеста не двигается, поэтому перетаскиваемый лист всё ещё накрывает точку отпускания.

Воспроизведено без браузера:

```
hits (topmost first): [ 'sheet-created-2', 'sheet-created-1' ]
сырые кандидаты     : [ 'sheet-created-2-top', 'sheet-created-1-inside', 'table' ]
после переупорядочивания: [ 'sheet-created-2-top', 'table', 'sheet-created-1-inside' ]

  try sheet-created-2-top   -> rejected CYCLE_DETECTED
  try table                 -> ACCEPTED   <-- победитель
```

То есть: `owned` = собственные поверхности перетаскиваемого листа, `parent` = его же текущая поверхность (`table`). Обе встают **перед** `sheet-created-1-inside`, который сырой список ранжировал правильно. Первый кандидат отсеивается как цикл, второй — `table` — принимается, и вложенность не происходит.

**Направление исправления** (проверено на том же стенде): исключить ветку перетаскиваемой сущности из `hits` и из списка кандидатов до ранжирования.

```
кандидаты без самого объекта: [ 'sheet-created-1-inside', 'table' ]
  try sheet-created-1-inside -> ACCEPTED   <-- победитель
```

Заодно стоит добавить unit-тест на `surfaceCandidatesForDrop` с `hits[0] === entity`, иначе класс ошибок вернётся: существующие unit-тесты этой функции передают `hits`, в которых перетаскиваемого объекта нет, поэтому регрессию поймал только e2e.

## Критично

### C1. Стоимость одной команды растёт линейно от числа вырезанных деталей

**Файлы:** [src/core/commands/index.js:359](src/core/commands/index.js:359), [src/core/validate.js:73](src/core/validate.js:73), [src/core/geometry/polygon.js:80](src/core/geometry/polygon.js:80)

`applyWorldCommand` валидирует **весь мир дважды** на каждую команду (вход и результат). `validateWorldState` для каждой вырезки вызывает `isSimplePolygon(entity.contour)` — алгоритм O(n²) по числу точек контура. Контуры не упрощаются: `normalizeClosedContour` удаляет только совпадающие точки с допуском 1e-9, а редактор пишет точку каждые 0.5 единицы документа, так что реальный контур «ножницами» — это 300–1000 точек.

Измерено на фикстурном мире (контуры по 600 точек):

| Вырезок в мире | Одна команда | Один дроп (try + dispatch) |
| --- | --- | --- |
| 0 | 0.03 мс | 0.07 мс |
| 1 | 4.1 мс | ~8 мс |
| 3 | 12.4 мс | ~25 мс |
| 5 | 20.4 мс | ~41 мс |

Это на десктопном V8. На планшете умножьте на 3–5. Пять нарисованных предметов — не экзотика, а нормальное состояние сцены через десять минут игры.

Три независимых рычага, любой из них снимает основную часть:

- Кэшировать результат `isSimplePolygon` по контуру — контур вырезки неизменяем после создания, проверять его при каждом дропе бессмысленно.
- Не валидировать вход в `applyWorldCommand`: он уже был выходом предыдущей проверенной команды. Это сразу −50 %.
- Упрощать контур (Ramer–Douglas–Peucker) при создании вырезки. Полезно и для рендера, и для размера сохранения.

### C2. Каждая команда применяется дважды

**Файл:** [src/app/interaction-controller.js:56](src/app/interaction-controller.js:56)

`commit()` сначала делает `store.try(cmd)` / `tryGroup`, а при успехе — `store.dispatch(cmd)` / `dispatchGroup`. Это удваивает C1. Хуже: пробы идут в цикле по кандидатам, поэтому неудачный дроп с тремя кандидатами стоит до шести полных применений команды, каждое с двумя валидациями мира.

`try` даёт полноценный `{ ok, world }` — можно использовать уже вычисленный мир, а не пересчитывать его. `WorldStore` понадобится метод вида «зафиксировать уже проверенный результат в истории».

### C3. Кэша текстур рисунков нет — есть только его название

**Файл:** [src/render/pixi-world-renderer.js:8](src/render/pixi-world-renderer.js:8)

```js
this.drawingCache = new DrawingTextureCache((drawing, lod) => ({ drawing: drawingForLod(drawing, lod), lod }), () => {}, ...)
```

`createTexture` возвращает обычный объект, `destroyTexture` — пустая функция. Никакого `RenderTexture` не создаётся. Класс `DrawingTextureCache` со всей его LRU-логикой и учётом видимости работает как мемоизация прореженного по LOD списка штрихов. Штрихи при этом каждый раз перерисовываются в `Graphics` через `drawDrawing`.

Дизайн-документ называет это главным средством против риска «Производительность пользовательских рисунков» (§14) и прямо требует кэширования в `RenderTexture` (§8.3). Отладочная панель показывает `cache N`, что создаёт ложное впечатление, будто кэш работает.

То же и на стороне редактора: [src/app/drawing-editor.js](src/app/drawing-editor.js) — `move()` вызывает `render()`, который перерисовывает **все** штрихи документа на каждое движение указателя. Нет слоя «уже зафиксированное», поверх которого рисуется только текущий штрих. Ровно тот случай, который дизайн-документ считал главным риском производительности.

## Баги

### D1. `createEntity` передаёт id вместо сущности в проверку размещения

**Файл:** [src/core/commands/index.js:97](src/core/commands/index.js:97)

```js
assertTarget(world, entity.id, world.surfaces[entity.surfaceId], entity.transform);
```

`assertTarget` ждёт объект сущности. Приходит строка. Два следствия:

**(а) Якорь сложенного листа считается неправильно.** `placementAnchor` проверяет `entity.kind !== "sheet"`, у строки `kind` нет, и возвращается сырой `{x, y}` вместо якоря со смещением на полширины. Валидация становится асимметричной — создать лист нельзя там, куда его можно переместить:

```
createSheet, transform {x:-71, y:477}, state "closed"  -> REJECTED OUTSIDE_PLACEMENT_AREA
тот же лист, созданный в безопасном месте и перемещённый в тот же transform -> OK
```

При этом `validateWorldState` ([src/core/validate.js:142](src/core/validate.js:142)) использует правильный якорь. Итого три места считают якорь по двум разным правилам.

**(б) Проверка цикла на этом пути мертва.** Внутри `assertTarget` сравнение `hostEntityId === entity.id` для строки даёт `undefined` и никогда не срабатывает. Сегодня безвредно (сущность новая, цикл невозможен), но это мина под любое будущее использование `createEntity` для переподключения.

### D2. `cut()` падает с TypeError при устаревшем `entityId`

**Файл:** [src/app/drawing-editor.js:53](src/app/drawing-editor.js:53)

```js
const sourceEntity = ..., pose = sourceEntity ? getEntityWorldTransform(...) : { x: 300, y: 300 };
const result = this.store.dispatch({ ..., worldPosition: { x: pose.x + sourceEntity.width + 45, ... } });
```

Защита от отсутствия `sourceEntity` есть, но следующая же строка разыменовывает `sourceEntity.width` без неё. Проверено:

```
cut() THREW: TypeError - Cannot read properties of undefined (reading 'width')
```

Достижимый путь: открыть редактор на объекте → нажать «отменить» в панели редактора, если объект был создан последней командой → объект исчезает из мира, `this.entityId` протухает → ножницы → падение. `main.js` от этого защищается (`update()` сбрасывает `ui.selectedEntityId`), а редактор — нет, он держит собственную копию `entityId` и никогда её не сверяет.

### D3. `holdEntity` разыменовывает отсутствующий шаблон

**Файл:** [src/core/commands/index.js:231](src/core/commands/index.js:231)

```js
const template = world.rules.templates[cat.templateId], held = entity.item === true;
const local = localPose && (held ? { ...localPose, x: template.viewBox.x + ... } : localPose);
```

Проверки на `template` нет, в отличие от `requireTemplate`, который используется во всех соседних командах.

### D4. Программные ошибки маскируются под доменные отказы

**Файл:** [src/core/commands/index.js:368](src/core/commands/index.js:368)

```js
const normalized = error instanceof CoreError ? error : fail("INVALID_REFERENCE", error.message);
```

Любой `TypeError` (как в D3) превращается в `{ ok: false, error: { code: "INVALID_REFERENCE" } }`. Интерфейс покажет «Действие невозможно», а не упадёт, и баг проживёт долго. Стоит либо пробрасывать не-`CoreError` наружу, либо давать отдельный код `INTERNAL_ERROR` и писать в консоль в DEV.

### D5. `depth()` без защиты от битой ссылки и цикла

**Файл:** [src/render/pixi-world-renderer.js:28](src/render/pixi-world-renderer.js:28)


Нет проверок ни на отсутствующую сущность (TypeError), ни на цикл (вечный цикл). Ядро такое состояние не пропустит, но `getSurfaceCandidates` работает с `this.world` напрямую и вызывается на каждое отпускание указателя. Все остальные обходы предков в проекте (`buildWorldMatrix`, `isEntityVisibleQuery`, `isInEntityBranch`) защиту имеют — этот выбивается.

## Важное

### E1. Тестовые датасеты фикстуры в продакшен-коде

**Файл:** [src/app/main.js:7](src/app/main.js:7)

`update()` на каждом вызове пишет в `main.dataset` поля, захардкоженные под конкретные id фикстуры:

```js
main.dataset.catBlueSurface     = store.world.entities["cat-blue"]?.surfaceId ?? "";
main.dataset.notebookHomeAZ     = String(store.world.entities["notebook-home-a"]?.zIndex ?? "");
main.dataset.notePinkSurface    = store.world.entities["note-pink"]?.surfaceId ?? "";
main.dataset.createdSheetSurface= store.world.entities["sheet-created-2"]?.surfaceId ?? "";
main.dataset.orangeAttachments  = ...
```

Это тестовые крючки в коде, который выполняется у игрока. Кроме того, `update()` вызывается на **каждый** `pointermove` во время перетаскивания, а строка `visibleEntities` для этого перебирает все сущности с `isEntityVisible` (обход предков на каждую) и сортирует. Отладочная панель за `import.meta.env.DEV` спрятана правильно — эти поля почему-то нет.

Стоит собрать их в одну функцию за флагом `import.meta.env.DEV`, а e2e-тесты перевести на обобщённые селекторы (`data-entity-<id>-surface`) вместо перечисления id фикстуры.

### E2. Класс патчит собственный прототип

**Файл:** [src/render/pixi-world-renderer.js:33](src/render/pixi-world-renderer.js:33)

Сразу после тела класса `PixiWorldRenderer.prototype.render` сохраняется в переменную и перезаписывается обёрткой. В итоге у класса два метода `render`, оба в одном файле, и определение, которое читатель видит первым, — не то, что вызывается. Это чистые два метода: `renderFrame(world, ui)` и `render(world, ui, events)`, вызывающий первый.

### E3. Лишний полный проход на кадр ради отладочной цифры

**Файл:** [src/render/pixi-world-renderer.js:30](src/render/pixi-world-renderer.js:30)

`fullOrder = this.displayOrder(world, ui)` используется ровно один раз — в `culledObjects: fullOrder.length - renderOrder.length` для отладочной панели. При этом `culledDisplayOrder` внутри себя вызывает `displayOrder` ещё раз. Итого `paintOrder` (обход всех сущностей с проверкой видимости для каждой) выполняется на кадр дважды. Замерено: при 800 сущностях это ~1.3 мс на кадр — не катастрофа сегодня, но платить за это в каждом кадре ради одной цифры не нужно. `culledDisplayOrder` может вернуть и порядок, и число отсеянных.

### E4. Удалить объект из интерфейса невозможно

`deleteEntity` реализован в ядре и покрыт тестами, но в `main.js` и `drawing-editor.js` он не вызывается ни разу. Дизайн-документ §7.2 перечисляет «удалить» среди действий выбранного объекта.

Это смыкается с C1: каждая неудачная вырезка навсегда добавляет стоимость **каждой** последующей команде, и убрать её игрок не может.

### E5. Ошибка старта даёт белый экран

**Файл:** [src/app/main.js:16](src/app/main.js:16)

`const templates = await loadCatTemplates();` — top-level await без обработки. Если `fetch` SVG не прошёл, модуль падает с необработанным reject, `#app` остаётся с уже вставленной разметкой, но без canvas и без единого сообщения. `loadCatTemplates` также падает, если у SVG нет `viewBox` или нет `polygon[data-silhouette]`.

### E6. «Начать новый мир» стирает мир без подтверждения

Кнопка стоит в одном ряду с «Новый кот» и «Новая одежда», нажимается одним кликом и заменяет сцену вместе с историей undo. Автосохранение перезаписывается следующим же `store.subscribe`. Восстановить нечем.

### E7. Поворот молча не срабатывает

**Файл:** [src/app/main.js:53](src/app/main.js:53)

Обработчики `left`/`right` — единственные, которые не проверяют `result.ok` и не зовут `notify`. Если поворот выводит якорь за пределы поверхности, объект просто не двигается без объяснений.

### E8. Ни один компонент не убирает за собой слушателей

`InteractionController.bind()` вешает слушатели на `canvas`, `window` и `document`; `DrawingEditor.bind()` — на `window` и `ResizeObserver`; `this.unsubscribe` в редакторе сохраняется, но не вызывается никогда. Для одностраничного приложения без роутинга это не течёт в проде, но мешает тестам и HMR.

### E9. Длина строк

Максимальная длина строки: 3382 символа в `pixi-world-renderer.js`, 2787 в `main.js`, 1958 в `interaction-controller.js`. Метод `render` — одна строка на 3.4 КБ. Это не вкусовщина: при таком форматировании `git diff` бесполезен (любая правка = «строка изменилась целиком»), а привязка ошибки к строке ничего не локализует. Один прогон Prettier с `printWidth` 120 и `.editorconfig` окупятся на первом же дебаге.

## Соответствие дизайн-документу

**Соблюдено:** граница ядра и представления (§8.1), ответственность ядра (§8.2), форма `applyCommand` и детерминизм (§8.5), нормализованные словари и версионированное сохранение (§9.1), разделение доменного и временного состояния (§9.2), все десять инвариантов (§10), набор инструментов рисования (§6.1), камера и жесты (§7.1–7.2).

**Расхождения:**

1. **Кэширование в `RenderTexture` (§8.3, §14)** — не реализовано, см. C3. Это единственная названная в документе мера против главного технического риска.
2. **Действие «удалить» (§7.2)** — есть в ядре, недоступно в интерфейсе, см. E4.
3. **«Получить фигурку рядом с выбранной областью стола» (§7.3)** — новые кот, одежда, лист и тетрадь создаются по захардкоженным координатам (`{x:560,y:300}`, `{x:760,y:390}`, `535 + createdId*12`). Выбранная область не учитывается, объекты складываются лесенкой в одном месте.
4. **Структура каталогов (§8.5)** — фактическая раскладка площе плана: нет `core/history/`, `core/persistence/`, `app/controllers/`, `app/tools/`, `app/store/`, `ui/components/`, а `rendering/pixi` стал `render/`. Для соло-PoC это разумное упрощение, но документ стоит привести в соответствие, иначе он перестаёт быть картой.

**Отдельно — правило из `AGENTS.md`.** Инвариант запрещает снаппинг для всех обычных объектов и разрешает его только для одежды (`entity.wearable`) и «предметов, явно помеченных как размещаемые на коте» (`entity.item`). Но [src/core/commands/index.js:302](src/core/commands/index.js:302) ставит `item: true` **всем** вырезкам без исключения, а [src/app/interaction-controller.js:56](src/app/interaction-controller.js:56) применяет `snapAnchorToSurface` ко всему, у чего есть `wearable || item`. В результате единственная категория объектов, которую игрок создаёт сам, целиком выведена из-под правила точного размещения. Формально буква правила соблюдена, но исключение поглотило основной случай. Стоит решить явно: либо `item` выставляется только при явном намерении, либо снаппинг ограничивается моментом привязки к коту, а не любым дропом.

## Тесты

69 unit-тестов, 21 e2e-сценарий (13 desktop + 8 persistence), production-smoke. Покрытие ядра предметное, а не формальное: циклы, видимость, round-trip сохранения, отказ загрузки без порчи текущего мира, атомарность групп.

Замечания:

- **e2e поймал то, что не поймали unit-тесты** (B1) — значит, unit-уровень `surfaceCandidatesForDrop` неполон: во всех его тестах перетаскиваемого объекта нет в `hits`, хотя в реальности он там почти всегда первый.
- **Нет теста на точную трансформацию при дропе вырезки.** `AGENTS.md` требует такие тесты для обычных объектов; вырезки формально выведены из-под правила через `item: true`, и именно поэтому регрессия в снаппинге вырезок сейчас никем не ловится.
- **Нет тестов на длинные контуры.** Все тестовые контуры — 4–11 точек, поэтому C1 в CI невидим. Достаточно одного теста с бюджетом времени на мир с несколькими 600-точечными вырезками.
- **`docs/release-checklist-stage-06.md` больше не отражает реальность:** там записано, что `npm run test:e2e` проходит, а на HEAD один сценарий падает. Чек-лист датирован 2026-09-01, регрессия пришла позже — но пометки об этом нет.
